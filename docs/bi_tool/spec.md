# 予測結果可視化BIツール 要件定義書

東京都の不動産価格予測モデルの**予測結果（`outputs/test_predictions.csv`）を可視化する
BIツール**の要件を定義する。グラフによる多面的な分析と、地図上での地理的な可視化
（行政区単位・駅単位のドリルダウン）を提供する。

- 想定実装: 既存スタックを活かした **Streamlit + Plotly + folium**（マルチページアプリ）
- 入力データ: `outputs/test_predictions.csv`（予測結果、約 7,900 行）
- 配置先（想定）: `app/pages/` 配下に BI ページを追加

---

## 1. 機能概要

### 1.1 目的と価値提案

| 観点 | 内容 |
|---|---|
| **目的** | 学習済みモデルの予測結果を、非エンジニアでも直感的に把握できる形で可視化する |
| **価値（分析者）** | 予測精度の弱点（誤差が大きいエリア・価格帯）を地理的・統計的に発見し、モデル改善につなげる |
| **価値（意思決定者）** | 行政区・駅単位の予測価格水準を地図で俯瞰し、エリア比較を素早く行える |
| **差別化** | 単なる精度指標の表示ではなく、「**どこで・どの価格帯で**外しているか」を地図とグラフで結びつけて示す |

### 1.2 ユーザーストーリー

- **US-1**: 分析者として、予測 vs 実測の散布図と誤差分布を見て、モデル全体の傾向を把握したい。
- **US-2**: 分析者として、地図上で誤差の大きい行政区／駅を一目で特定し、原因仮説を立てたい。
- **US-3**: 利用者として、地図上のアイコンをクリックし、その行政区／駅の平均予測価格・実測価格・誤差をポップアップで確認したい。
- **US-4**: 利用者として、価格帯・物件種類・面積・築年数でフィルタし、関心のあるセグメントだけを見たい。
- **US-5**: 意思決定者として、行政区別の予測価格ランキングを見て、エリアの相場感を比較したい。

### 1.3 成功基準（受け入れ条件）

| ID | 成功基準 | 計測方法 |
|---|---|---|
| AC-1 | 予測結果CSVを読み込み、5種類以上のグラフを表示できる | 目視・E2E |
| AC-2 | 地図上に駅単位／行政区単位の集計値を可視化できる | 目視 |
| AC-3 | 地図アイコンのクリックで、当該エリアの集計指標をポップアップ表示できる | 操作確認 |
| AC-4 | フィルタ操作がグラフ・地図の両方に即座に反映される | 操作確認 |
| AC-5 | 初期表示が 5 秒以内に完了する（約 8,000 行・集計後） | 計測 |

## 2. 機能要件

### 2.1 必須機能（Must Have）

#### M-1. データ読み込み・前処理
- `outputs/test_predictions.csv` を読み込む（パスは設定で切り替え可能）。
- 緯度経度が欠損する行（駅マスタ未マッチ）は地図表示から除外し、件数を明示する。
- `@st.cache_data` で読み込み・集計結果をキャッシュする。

#### M-2. KPIサマリ（ヘッダ指標）
- 全体の評価指標をカード形式で表示: 件数, R²(log), MAE(円), RMSE(円), MAPE(%), Median APE(%)。
- 指標の意味は `docs/../modeling/evaluation_metrics.md` を参照リンクとして併記。

#### M-3. BIグラフ（Plotly）
| グラフ | 内容 | 列 |
|---|---|---|
| 予測 vs 実測 散布図 | `y=x` 基準線つき。点の色＝APE | `actual_price_yen`, `pred_price_yen`, `ape_percent` |
| 誤差分布ヒストグラム | 残差(円) / APE(%) を切替表示 | `error_yen`, `ape_percent` |
| 価格帯別 件数・精度 | 価格帯ごとの件数と平均APE | `actual_price_band`, `ape_percent` |
| 行政区別 ランキング | 平均予測価格／平均APEの棒グラフ（Top-N） | `市区町村コード`, `pred_price_yen` |
| 駅別 ランキング | 同上（駅単位） | `最寄駅：名称`, `pred_price_yen` |
| 特徴量との関係 | 面積・築年数 vs 価格の散布図 | `面積（㎡）`, `築年数`, `pred_price_yen` |

#### M-4. 地図可視化（folium + streamlit-folium）
- **粒度の切替**: 「駅単位」「行政区単位」をトグルで選択。**初期表示は行政区単位**をデフォルトとする。
- **駅単位**: `最寄駅：緯度／経度` に集計マーカーを配置。マーカーサイズ／色＝予測価格 or APE。
- **行政区単位**: `市区町村コード` をキーに東京都市区町村のGeoJSONでコロプレス（塗り分け）地図を描画。
- **指標の切替**: 表示する色分け指標を「平均予測価格」「平均実測価格」「平均APE」から選択。

#### M-5. クリック時ポップアップ（コア要件）
- 地図上のマーカー／区画をクリックすると、ポップアップで以下を表示する。

| 項目 | 駅単位 | 行政区単位 |
|---|---|---|
| 名称 | 駅名 | 市区町村名（コード） |
| 物件件数 | ○ | ○ |
| 平均／中央 予測価格(円) | ○ | ○ |
| 平均／中央 実測価格(円) | ○ | ○ |
| 平均APE / Median APE(%) | ○ | ○ |
| 代表的な物件種類・価格帯 | ○ | ○ |

#### M-6. フィルタ（サイドバー）
- 行政区（複数選択）、最寄駅（複数選択）、物件種類、価格帯、面積レンジ、築年数レンジ、山手線内側フラグ。
- フィルタはグラフ・地図・KPIすべてに連動する。

### 2.2 あると良い機能（Nice to Have）

- **N-1**: 地図クリックでサイドのグラフ群を当該エリアに自動フィルタ（地図⇄グラフの双方向連携）。
- **N-2**: フィルタ後データ／集計結果のCSVダウンロードボタン。
- **N-3**: 残差の大きいワースト物件テーブル（誤差要因の個別確認）。
- **N-4**: 駅からの距離・容積率などモデル特徴量と誤差の相関ヒートマップ。

### 2.3 将来的な拡張（Future Enhancement）

- **F-1**: 任意物件のインタラクティブ予測（属性を入力→価格予測＋SHAPで根拠表示）。`app/streamlit_app.py` 本体と統合。
- **F-2**: 時系列（取引四半期）での予測価格トレンド表示。
- **F-3**: 複数モデル（LightGBM / XGBoost）の予測比較ビュー。
- **F-4**: Streamlit Community Cloud へのデプロイと公開URL化。

## 3. 非機能要件

### 3.1 パフォーマンス
- 初期表示 5 秒以内（集計後データで描画）。
- 地図は**集計後の点**（駅 約600件 / 行政区 約62件）を描画し、生の約8,000点はそのまま打点しない。
- 読み込み・集計は `@st.cache_data`、重い前処理は事前集計したParquet/CSVを利用。

### 3.2 セキュリティ
- 予測結果はオープンデータ由来で個人情報を含まないが、**個別住所の番地レベルは表示しない**（地区名・駅単位まで）。
- 外部GeoJSON/タイルは信頼できるソース（国土数値情報・OpenStreetMap等）に限定。
- ファイルパス等の設定は環境変数／`configs/` で管理し、ハードコードしない。

### 3.3 ユーザビリティ
- 金額は「**億・万」併記**で表示する（例: `54,000,000` → `5,400万円`、`120,000,000` → `1億2,000万円`）。元の円値はツールチップ等で補助表示する。
- 色は誤差の大小が直感的に分かる連続カラースケール（例: 低誤差=青 → 高誤差=赤）。
- 凡例・指標の定義（特にAPE等）にツールチップ／説明リンクを付ける。
- 日本語UI。地図・グラフのラベルも日本語。

## 4. 技術的考慮事項

### 4.1 既存システムへの影響
- `app/streamlit_app.py` は現状スタブ。**マルチページ構成に統合**する（確定）。`streamlit_app.py` をエントリ／予測アプリとし、BIツールを `app/pages/` 配下のページとして追加。両者は同一アプリ内で共存する。
- 依存追加: `folium`, `streamlit-folium`（地図クリック・ポップアップ用）。`plotly`・`streamlit`・`pandas` は導入済み。
- `src/` のモデル・前処理コードへの変更は不要（読み取り専用で予測結果CSVを消費）。
- 集計ロジックは再利用性のため `src/` 配下のモジュール（例: `src/visualization/aggregate.py`）として切り出し、UI（`app/`）と分離する。

### 4.2 必要な技術スタック
| 区分 | 技術 | 用途 | 状態 |
|---|---|---|---|
| アプリ基盤 | Streamlit | マルチページUI | 導入済 |
| グラフ | Plotly | 散布図・分布・ランキング | 導入済 |
| 地図 | folium + streamlit-folium | クリック可能なマーカー／コロプレス＋ポップアップ | **要追加** |
| データ処理 | pandas | 集計 | 導入済 |
| 地理境界 | 東京都市区町村 GeoJSON（国土数値情報 等） | 行政区コロプレス | **要追加（データ）** |

> 地図ライブラリ選定: クリック→ポップアップ要件には Leaflet ベースの **folium** が最も素直。
> 大量点の高速描画が必要になれば `pydeck` を代替候補とする。

### 4.3 データモデルの設計

#### 入力（`outputs/test_predictions.csv` の利用列）
- **地理キー**: `市区町村コード`, `住所`, `最寄駅：名称`, `最寄駅：緯度`, `最寄駅：経度`
- **予測結果**: `actual_price_yen`, `pred_price_yen`, `error_yen`, `abs_error_yen`, `error_rate_percent`, `ape_percent`, `actual_price_band`
- **属性（フィルタ／分析用）**: `種類`, `面積（㎡）`, `築年数`, `都市計画`, `最寄駅：距離（分）`, `山手線内側`

#### 集計テーブル（アプリ内で生成）
| テーブル | 粒度キー | 主な集計列 |
|---|---|---|
| `agg_station` | `最寄駅：名称`（+代表緯度経度） | 件数, 予測価格 mean/median, 実測価格 mean/median, APE mean/median |
| `agg_ward` | `市区町村コード`（+`市区町村名`） | 同上 |

- `市区町村名` は `市区町村コード` ↔ 名称マスタ（JISコード）で対応付ける。GeoJSONの結合キーもこのコードに統一する。
- 緯度経度欠損行は地図集計から除外（グラフ・KPIには含める）。除外件数をUIに表示。

## 5. 実装計画

### 5.1 フェーズ分け
| フェーズ | 内容 | 対応要件 |
|---|---|---|
| **P0: 基盤** | データ読込・キャッシュ・集計モジュール（`src/visualization/aggregate.py`）・ユニットテスト | M-1 |
| **P1: BIグラフ** | KPIサマリ＋Plotlyグラフ群＋サイドバーフィルタ | M-2, M-3, M-6 |
| **P2: 地図（駅単位）** | folium マーカー＋クリックポップアップ | M-4(駅), M-5(駅) |
| **P3: 地図（行政区）** | GeoJSON調達＋コロプレス＋ポップアップ | M-4(区), M-5(区) |
| **P4: 連携・仕上げ** | 地図⇄グラフ連携、CSV出力、UI調整 | N-1, N-2, N-3 |

### 5.2 概算工数（目安）
| フェーズ | 工数(人日) |
|---|---|
| P0 基盤 | 1.0 |
| P1 BIグラフ | 1.5 |
| P2 地図(駅) | 1.5 |
| P3 地図(行政区) | 2.0 |
| P4 連携・仕上げ | 1.0 |
| **合計** | **約 7 人日** |

### 5.3 リスクと対策
| リスク | 影響 | 対策 |
|---|---|---|
| 行政区GeoJSONの調達・コード整合 | P3 遅延 | 早期に国土数値情報のGeoJSONを確保し、`市区町村コード`での結合を先に検証 |
| `streamlit-folium` のクリックイベント仕様 | M-5 実現性 | P2 冒頭でPoC（クリック→戻り値取得）を実施 |
| 緯度経度欠損（駅マスタ未マッチ）の多さ | 地図の網羅性低下 | 欠損率を計測しUIに明示。駅名正規化で改善（前処理側と連携） |
| 生データ約8,000点の描画負荷 | 表示遅延 | 集計後の点のみ描画。必要に応じ事前集計ファイル化 |
| `市区町村コード`→名称マスタの欠落 | ラベル表示不全 | JISコードマスタを `configs/` に同梱 |
